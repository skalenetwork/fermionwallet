为何是现在

增加签名人
并不能让多签抵御量子攻击

每一位 Safe 所有者都用 ECDSA 签名。足够强大的量子计算机能攻破 ECDSA，而且是同时攻破您所有的签名人。持有十年的资产，需要一种能撑过那一天的签名。

多签是治理手段

它决定谁可以签名，但当签名算法本身被攻破时，它无能为力。

硬件密钥防止盗窃

但它们挡不住同一曲线上的伪造签名：密钥根本不需要离开设备。

链下策略只是建议

链上不会查询的策略引擎是可以被绕过的。最终决定权必须在链上。

工作原理

两个相互独立的签名，
一条执行路径。

FermionGuard 是一个 Safe Guard，即 Safe 官方的执行前钩子。所有者照常签名。只有当交易同时附带一个匹配的后量子批准时，Guard 才会放行。

签名 1：保持不变

您的 Safe 所有者

同样的所有者、同样的门槛、同样的硬件钱包。防范失职的操作人员、设备丢失和内部故障。

签名 2：新增

一个后量子批准

一位指定的量子管理员使用 Ledger 上的 XMSS 密钥批准每一笔转账。防范签名人被攻破、批准被重放、授权额度被盗取，以及未来的量子攻击。

排队

操作人员在 Safe{Wallet} 中提交一笔转账，所有者照常签名。

标记

FermionGuard Safe App 将其标记为 🟡 需要量子授权。

审核

管理员审核交易内容，这些内容由两个相互独立的数据源解码得出。

批准

Ledger 显示每一个受约束的字段。长按即可批准。

执行

该行变为 🟢。任何人都可以执行；Guard 会检查并消耗这一批准。

管理员清楚看到自己批准的内容

批准对应的是确切的交易，而不是意图

一个批准会写明 Safe、链、代币、收款人、金额和有效期。如果有人事后修改了排队中的交易，批准便不再匹配，Guard 会拒绝它。

  • 有时限：每个批准只在您选定的时间窗口内有效。
  • 一次性：交易执行的那一刻即被消耗。
  • 双重核对：在解锁签名之前，交易内容必须在两个相互独立的数据源上一致。
  • 拒绝可见：拒绝与批准一样会被签名并记录。

不做盲签：设备会显示 Guard 约束的每一个字段

在您团队已经在用的工具中运行

FermionGuard 以 Safe{Wallet} 内的 Safe App 和供管理员使用的 Ledger 应用两种形式提供。风险提示会在任何人签名之前，突出显示首次出现的收款人、异常金额，以及 Guard 本来就会拒绝的交易。

安全

难以绕过，
也绝不会把资产锁死。

Guard 是链上的最后一道否决，其设计确保密钥丢失或程序缺陷都永远无法冻结您的资金。

始终有退路

Ledger 丢了？所有者在 14 天公开倒计时后即可自行移除 Guard。损坏的设备永远不会锁死 Safe。

治理变更公开透明

移除 Guard 或更换所有者需要一个批准以及一段会通知所有所有者的 48 小时公开倒计时。

故障即关闭

Guard 不可升级，并配有可在事故时快速拒绝一切的暂停功能。没有管理员后门。

没有旁门

Safe 模块会绕过 guard，因此注册时要求未启用任何模块，或在 Safe 1.5+ 上配套安装 module guard。

不会被盗取授权额度

approve、permit 和 transferFrom 一律拒绝，批量交易会在链上逐笔检查。

无法被调包的密钥

所有者在各自的设备上共同签署密钥的完整公开根，因此被攻破的网站无法替换成另一把密钥。

治理变更缓慢而公开；取消则很快

即使量子密钥被盗，也无法悄悄夺取控制权

攻击者即使拿到管理员的 Ledger，没有您所有者的签名也无法转移资金，而且不经过一段您的所有者可以取消的 48 小时公开倒计时，也无法移除 Guard。

后量子签名，
在 EVM 中验证

XMSS 只依赖哈希运算，因此链可以直接验证它：无需预言机，也无需可信服务器。验证器是对 RFC 8391 的独立实现，我们也会准确说明其证明的覆盖范围：每一个 RFC 基础原语，以及拒绝畸形输入的各项检查，都已针对 RFC 的逐行转写、对所有输入进行了机器验证。将它们组合成最终接受或拒绝合规签名的根比较这一步，则由人工论证，在树高为 2 时进行了符号检查，并用 h = 4、10 和 20 的 RFC 向量加以固定。

从设计上杜绝叶子复用

XMSS 是有状态的：复用一次性叶子会让攻击者得以伪造签名。Ledger 在交出签名之前会先提交其计数器，合约也维护一个已用叶子的位图，任何复用都会被回滚。

function _verifyAndConsumeXmss(
    bytes32 keyId,
    bytes32 digest,
    bytes calldata xmssSignature
) internal {
    XMSS.Signature memory sig = abi.decode(xmssSignature, (XMSS.Signature));
    BitMaps.BitMap storage used = _usedLeaves[xmssRoot(keyId)];  // per KEY, not per registration
    if (used.get(sig.leafIdx)) revert LeafAlreadyUsed(keyId, sig.leafIdx);

    if (!XMSS.verify(digest, sig, publicKey(keyId), treeHeight(keyId)))
        revert InvalidXmssSignature();  // whole tx rolls back

    used.set(sig.leafIdx);                // burn the one-time leaf
    emit LeafConsumed(keyId, sig.leafIdx, digest);
}

常见问题

团队最先问的问题

我们需要转移资产或更改 Safe 吗？

不需要。您只是在现有的 Safe 上安装一个 Guard。所有者、门槛、历史记录和地址完全不变。

如果管理员的 Ledger 丢了怎么办？

您的所有者无需量子密钥，在 14 天公开倒计时后即可自行移除 Guard。如果该请求并非正当，所有者可在此期间随时用一笔普通 Safe 交易取消它。丢失的设备永远无法永久锁死您的 Safe。

这会拖慢我们的转账吗？

每笔转账需要管理员在 Ledger 上额外批准一次。批量交易——比如最多 100 笔转账的工资发放——整批只需一次批准。

gas 成本是多少？

验证后量子签名约需 745,000 gas，在创建批准时支付一次（在 h = 20 时实测为 745,003 gas）。交易执行时的检查只是一次查询。

支持哪些 Safe？

Safe v1.3.0 及以上版本。Safe 不能启用任何模块，因为模块会绕过 guard；或者使用 Safe 1.5+ 并同时安装 FermionGuard 的 module guard。Safe 也不能设置 fallback handler：ERC-20 代币和 ETH 可正常使用，但签名消息功能（Permit、CowSwap 订单、登录）以及通过 safeTransferFrom 接收 NFT 暂不支持。

为什么用 XMSS，而不是 ML-DSA 或 Falcon？

XMSS 是 NIST 批准（SP 800-208）的基于哈希的签名，EVM 验证它只需约 1M gas。而 ML-DSA、Falcon 等格密码方案，目前在链上验证要花费数千万 gas。

现在能用于生产环境吗？

还不能。后量子验证器已按上文所述的范围针对 RFC 8391 做了机器验证，Guard 合约也已实现并测试，但目前尚未经过任何审计；Ledger 应用和 Safe App 仍在开发中，任何主网部署之前都必须完成外部审计。申请抢先体验，成为首批接入的团队之一。
